## 🎯 Commit Workflow (각 커밋 단위)

### Step-by-Step Process

```
1. 코드 작성 완료
   ↓
2. 빌드 & 테스트 병렬 실행 (서브 에이전트 활용)
   - Task 1: ./gradlew build
   - Task 2: ./gradlew test
   ↓
3. 결과 분석
   ├─ 이슈 발견 → 수정 → Step 2로 돌아가기
   └─ 모두 통과 → Step 4
   ↓
4. 사용자 확인 요청
   - 변경사항 요약 (git diff --stat)
   - 빌드 결과
   - 테스트 결과
   ↓
5. 사용자 승인 → 커밋 실행
```

### Quality Gates

**각 커밋 전 필수 체크**:
- ✅ `./gradlew build` 성공
- ✅ `./gradlew test` 통과
- ✅ 사용자 확인 완료

**실패 시 동작**:
- 에러 메시지 분석
- 자동 수정 시도
- 다시 빌드/테스트 실행
- 반복 (최대 3회)

## 📝 Commit Message Format (Angular Convention)

### Language
**English ONLY** (following industry standard)

### Format
```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### Types (Required)
- `feat`: New feature
- `fix`: Bug fix
- `refactor`: Code refactoring (no functionality change)
- `test`: Test additions or modifications
- `docs`: Documentation changes
- `chore`: Build, config, or dependency changes
- `style`: Code formatting (no logic change)
- `perf`: Performance improvements
- `ci`: CI configuration changes

### Scope (Optional but Recommended)
- The module or area affected
- Examples: `repo`, `ui`, `api`, `service`, `viewmodel`, `domain`

### Subject (Required)
- Use imperative mood ("add" not "added" or "adds")
- Start with lowercase
- No period at the end
- Keep under 50 characters
- Be specific and descriptive

### Prohibited Content (절대 금지)

❌ **NEVER include**:
- "Co-Authored-By: Claude <noreply@anthropic.com>"
- "🤖 Generated with [Claude Code](https://claude.com/claude-code)"
- "Generated by Claude"
- "Created with AI assistance"
- Any Claude or AI attribution

### Body (Optional)
- Separate from subject with blank line
- Explain WHAT and WHY, not HOW
- Max 72 characters per line
- Use bullet points for multiple changes

### Footer (Optional)
- Reference issues: `Refs #123`, `Closes #123`, `Fixes #123`
- Breaking changes: `BREAKING CHANGE: description`

---

❌ **Bad Examples**:
```
feat: DefaultDecksRepo 구현 추가  (Korean)
Add DefaultDecksRepo  (No type/scope)
feat: add repo  (Too vague, no scope)

🤖 Generated with Claude Code  (Claude attribution)
Co-Authored-By: Claude <noreply@anthropic.com>
```

✅ **Good Examples**:
```
feat(repo): add DefaultDecksRepo implementation

- Implement DecksRepo interface
- Connect RemoteTournamentDataSource
- Add deck statistics aggregation logic
```

```
fix(ui): resolve deck detail loading state issue

- Apply UiState sealed class pattern
- Add CircularProgressIndicator for loading
- Handle error states properly
```

```
test(repo): add comprehensive tests for DefaultDecksRepo

Refs #24
```

```
refactor(viewmodel): improve error handling in TierDecksViewModel
```

## 💻 Code Style Rules

### Comments Policy

**NO comments unless absolutely necessary**:

❌ **Prohibited**:
- KDoc comments (`/** */`)
- Inline comments (`//`)
- Block comments (`/* */`)
- TODOs in production code

✅ **Exception (Only when necessary)**:
- Complex algorithm explanation
- Non-obvious business logic
- Workaround for external library bug

**Example**:

❌ **Bad (unnecessary comment)**:
```kotlin
// DefaultDecksRepo 구현
class DefaultDecksRepo(
    private val dataSource: RemoteTournamentDataSource
) : DecksRepo {
    // 모든 티어 덱을 가져옴
    override suspend fun allTierDecks(): List<DeckInformation> {
        // 데이터 소스에서 조회
        return dataSource.fetchDecks()
    }
}
```

✅ **Good (self-documenting code)**:
```kotlin
class DefaultDecksRepo(
    private val dataSource: RemoteTournamentDataSource
) : DecksRepo {
    override suspend fun allTierDecks(): List<DeckInformation> {
        return dataSource.fetchDecks()
    }
}
```

✅ **Acceptable (complex logic)**:
```kotlin
fun calculateWinRate(wins: Int, losses: Int): Float {
    // 소수점 둘째 자리까지 반올림
    // 예: 15승 5패 = 0.75 (75%)
    val total = wins + losses
    if (total == 0) return 0f
    return (wins.toFloat() / total * 100).roundToInt() / 100f
}
```

### Code Clarity

**Prefer**:
- Self-explanatory variable names
- Small, focused functions
- Clear class/interface names
- Descriptive parameter names

## 🌿 Branching Strategy

### Branch Naming Convention

```
<type>/<description>
```

**Types**:
- `feature/`: 새 기능 추가
- `fix/`: 버그 수정
- `refactor/`: 코드 개선
- `chore/`: 빌드/설정 변경

**Examples**:
```
feature/tier-decks-api
feature/deck-detail-screen
feature/error-handling-system
fix/loading-indicator
refactor/view-model-cleanup
chore/proguard-config
```

### Branch Lifecycle

1. **Create**: `git checkout -b feature/tier-decks-api`
2. **Work**: Multiple commits (각 커밋 전 빌드/테스트)
3. **Review**: 브랜치 작업 완료 후 전체 검토
4. **Push**: 사용자 확인 후 `git push origin feature/tier-decks-api`

## 🔧 Build & Test Execution

### Parallel Execution

**각 커밋 작업 완료 시 자동 실행**:

```kotlin
// 서브 에이전트를 사용한 병렬 실행
Task 1 (background): ./gradlew build
Task 2 (background): ./gradlew test

// 동시 실행, 모두 완료될 때까지 대기
// 하나라도 실패 시 → 에러 분석 → 수정 → 재실행
```

### Error Handling

**빌드 실패 시**:
1. 에러 로그 분석
2. 컴파일 에러 수정
3. 다시 빌드 실행
4. 성공할 때까지 반복 (최대 3회)

**테스트 실패 시**:
1. 실패한 테스트 확인
2. 테스트 또는 코드 수정
3. 다시 테스트 실행
4. 성공할 때까지 반복 (최대 3회)

### Retry Limit

- **최대 재시도**: 3회
- **3회 초과 시**: 사용자에게 에러 리포트 및 도움 요청

## 🔄 Git Sync Rules

### Before Starting New Feature

**dev 브랜치 최신화 필수**:
```bash
# dev 브랜치 최신화
git checkout dev
git pull --rebase origin dev

# feature 브랜치 생성
git checkout -b feature/new-feature
```

### During Long-Running Feature

**주기적으로 dev 동기화 (권장: 1-2일마다)**:
```bash
git fetch origin dev
git rebase origin/dev
```

**목적**:
- Conflict 최소화
- dev의 최신 변경사항 반영
- 최종 merge 시 문제 예방

### After Completing Feature

**최종 동기화 및 Push**:
```bash
# 최종 동기화
git fetch origin dev
git rebase origin/dev

# Conflict 해결 후 (있는 경우)
# ... resolve conflicts ...
git add <resolved-files>
git rebase --continue

# Push
git push origin feature/new-feature
```

## ⚠️ Force Push Rules

### ALLOWED (허용되는 경우)

- ✅ **자신의 feature 브랜치**: `git push --force-with-lease origin feature/my-work`
- ✅ **Rebase 후**: origin/dev와 동기화 후 Conflict 해결 완료 시
- ✅ **Commit 수정 후**: 본인 브랜치에서 커밋 amend 또는 rebase 후

### PROHIBITED (절대 금지)

- ❌ **main/dev 브랜치**: 절대 force push 금지
- ❌ **타인이 사용 중인 브랜치**: 협업 브랜치는 force push 불가
- ❌ **이미 PR 생성된 브랜치**: 리뷰 진행 중인 경우 (새 커밋 추가만 가능)

### Safe Force Push

**ALWAYS use `--force-with-lease`**:
```bash
# ✅ 안전한 방법 (권장)
git push --force-with-lease origin feature/my-branch

# ❌ 위험한 방법 (절대 사용 금지)
git push --force origin feature/my-branch
```

**`--force-with-lease` 장점**:
- Remote에 예상치 못한 변경사항이 있으면 push 실패
- 타인의 작업을 실수로 덮어쓰는 것 방지
- 안전한 force push

### When Force Push is Needed

**시나리오 1: Rebase 후**
```bash
git fetch origin dev
git rebase origin/dev
# Rebase로 히스토리 변경 → force push 필요
git push --force-with-lease origin feature/my-branch
```

**시나리오 2: Commit 수정 후**
```bash
git commit --amend
# 커밋 수정 → force push 필요
git push --force-with-lease origin feature/my-branch
```

## 🤖 Custom Commands Integration

### Overview

This project has custom commands that automate issue resolution. They **MUST follow** all git-workflow rules.

### Available Commands

#### 1. `/decompose-issue` - Break Down Large Tasks

**Purpose**: Split complex tasks into structured GitHub issues

**Usage**:
```bash
/decompose-issue --task "티어 덱 API 연동" --lang ko
/decompose-issue --task "Implement user authentication" --lang en
```

**Output**: Structured GitHub issues with labels, acceptance criteria, implementation notes

**When to Use**:
- Planning phase before implementation
- Large features need breakdown
- Creating structured GitHub issues

#### 2. `/solve-issue` - Automated Issue Resolution

**Purpose**: Complete end-to-end issue resolution with automation

**Usage**:
```bash
/solve-issue --issue 24                    # Default: main branch, Korean PR
/solve-issue --issue 72 --base dev        # From dev branch
/solve-issue --issue 28 --lang en         # English PR
```

**When to Use**:
- GitHub issue already exists
- Want automated analysis and parallel research
- Need comprehensive test coverage
- Prefer structured workflow

**Important**: `/solve-issue` follows ALL git-workflow rules:
- ✅ User confirmation before EACH commit
- ✅ Build & test before commit
- ✅ Angular commit convention (English)
- ✅ No Claude attribution

### Workflow Comparison

**Manual Development** (Current Approach):
```bash
# 1. Create branch
git checkout -b feature/tier-decks-api

# 2. Implement (with Claude's help)
# ... coding ...

# 3. Build & test (parallel)
./gradlew build & ./gradlew test

# 4. User confirms → Commit
git commit -m "feat(repo): add DefaultDecksRepo implementation"
```

**Automated with /solve-issue**:
```bash

/solve-issue --issue 24 --base dev

# Claude will:
# - Fetch issue from GitHub
# - Create descriptive branch
# - Launch parallel research agents (up to 10)
# - Implement solution
# - ASK USER: "Commit implementation?" ← User confirms
# - Write tests in parallel
# - ASK USER: "Commit tests?" ← User confirms
# - Run validation (build/test/lint parallel)
# - If fails, fix and ASK USER again
# - Create PR
```

### Rules for Custom Commands

**All custom commands MUST**:
- ✅ Request user confirmation before EACH commit
- ✅ Show complete change summary (files, build, test results)
- ✅ Follow Angular commit convention (English)
- ✅ Run build & test before commit
- ✅ Never include Claude attribution
- ✅ Stop and ask if unsure

**User can**:
- Type "yes" → Proceed with commit
- Type "no" → Skip commit
- Type "modify" → Change commit message
- Type "stop" → Halt entire process

## 🎯 Summary

### Core Principles

1. **Quality First**: 빌드/테스트 통과 필수
2. **User Control**: 모든 커밋은 사용자 승인 후 (manual AND custom commands)
3. **Clean History**: Angular commit convention, English messages
4. **No Attribution**: Claude 관련 내용 절대 금지
5. **Self-Documenting**: 주석 없이 명확한 코드

### Automation Flow

```
코드 작성 → 빌드/테스트 (병렬) → 통과 확인 →
사용자 확인 → 승인 → 커밋
```

### Failure Flow

```
빌드/테스트 실패 → 에러 분석 → 자동 수정 →
재실행 → (반복 최대 3회) → 성공 또는 사용자 도움 요청
```
